# 非目标与已知边界

这份文档比功能和架构都重要。它回答用户心里那句话：

> **"这玩意会不会把我系统搞坏 / 骗我？"**

---

## 1. 明确不做

| 不做 | 原因 |
|---|---|
| 识别 agent | 黑名单必然不完备（见 architecture.md §1） |
| 监控整个文件系统 | 性能、隐私、噪声三杀 |
| 拦截网络 | 文件系统层管不了 |
| 拦截数据库 / 进程内存 | 不在 VFS 里 |
| 保护块设备直写（`dd of=/dev/sdX`） | 那是另一个威胁模型 |
| 假装能约束所有进程 | 见下面第 2 节 |

---

## 2. 已知边界

### 2.1 你没启动的进程

| 场景 | 能不能拦 | 说明 |
|---|---|---|
| 终端里 `codex` | ✅ 用 `gitjail run` 启动即可 | 推荐方式 |
| systemd 服务（OpenClaw） | ✅ 装 drop-in | `gitjail svc install` |
| VS Code 里的 Copilot / Cursor 后台 | ❌ | 它与 `code` 同 UID、同 namespace |
| 浏览器里的 agent | ❌ | 同上 |
| Docker 容器里的 agent | ⚠️ 取决于挂载 | 容器有自己的 namespace |
| 已经跑起来的进程 | ❌ | 无法事后收紧 namespace |

**为什么 IDE 插件拦不住：** 一个和你同 UID、同 mount namespace、又不是你启动的
进程，在文件系统层没有任何稳定特征可以和编辑器本身区分。这是物理限制，不是实现缺陷。

**缓解：** 降级为检测。

```bash
$ gitjail audit
⚠ 3 次写入来自未受限进程
  ~/code/proj/src/api.rs   pid 8123   code (vscode)
  建议: 用 gitjail run 启动，或为该应用安装 AppArmor 配置
```

### 2.2 复制出去

```bash
cp ~/code/proj/secret.txt /tmp/x    # 新 inode → 不受保护
```

拦不住，也不该拦——`cp` 是正常操作。如果这个文件本身是机密，用 `--hide`
让它根本看不见，而不是等它被复制。

### 2.3 读走再外传

文件系统层不知道网络。agent 读了内容，通过 HTTP / DNS / 剪贴板发出去，
VFS 无从知晓。

**这是 `--hide` 存在的理由：不给它读，比事后追它更可靠。**

### 2.4 代写（confused deputy）

agent 可以通过 IPC 让你信任的进程替它写：

- 通过 LSP 让编辑器改文件
- 通过 `xdotool` 往编辑器窗口里打字
- 通过 `dbus` 调用文件管理器

文件系统层无法区分「用户自己按的键」和「agent 模拟的按键」。

**缓解：** `kernel.yama.ptrace_scope=1` 挡住 ptrace；其余属于桌面安全范畴。

### 2.5 特权进程

如果 agent 以 root 运行，所有机制失效。它不是「受限进程」，它是 root。

**规则：不要用 `sudo gitjail run`。**

## 3. 故障时不做什么

| 故障 | 行为 |
|---|---|
| 策略文件损坏 | 降级为零保护，**不阻断开机** |
| daemon 未启动 | 拒绝启动 `gitjail run`，明确报错 |
| overlay 挂载失败 | 拒绝启动 agent，**不静默降级为可写** |
| audit 队列满 | 丢事件 + 告警，不阻塞强制平面 |

**原则：强制平面的失败不能扩散到强制平面之外。**

宁可 agent 起不来，也不能让「以为被保护」变成「实际没保护」。

---

## 4. 一句话

> 它保护的是**你声明的目录**，防的是**你启动的 agent** 的**文件写入**。
> 这三处之外的，它不承诺。
